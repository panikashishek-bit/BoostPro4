# Командные правила агента — рабочая папка Boost Pro

> Регламент твоего «штаба». Агент читает эти правила автоматически и работает по ним весь курс, как дисциплинированный сотрудник. Правила лежат в корне проекта и управляют именно им.
>
> ⚠️ Этот файл — для Codex. `CLAUDE.md` (Claude Code) содержит тот же набор правил. Меняешь одно — сразу правь и второе.

## Правила работы с репозиторием и проектом
1. **Документация в ногу с кодом.** При добавлении новой части проекта (бот, голос, API, второй бот) сразу обновляй `./docs/architecture.md` — не «потом», а в том же заходе. База знаний бота (то, что он отвечает клиентам) живёт отдельно, в `./faq/`; технические детали туда не попадают.
   *Почему:* через неделю никто не помнит, как устроена связка. Устаревшая архитектурная дока хуже её отсутствия — агент прочитает её и построит по ней неверное решение.
2. **Сначала подтяни свежее — не затри чужое.** Перед отправкой в общий репозиторий (push): сначала `git fetch` + `git pull --rebase`; убедись, что не расходишься с общим репозиторием и не затираешь чужие изменения.
3. **Короткие понятные коммиты.** Сохраняй изменения небольшими осмысленными порциями с понятным сообщением.
4. **Никогда не сохраняй секреты.** Пароли, токены, ключи — только в `.env` (в `.gitignore`); в репозиторий идёт `.env.example` со списком имён без значений. В чат агенту секреты не передавать.
5. **Файлы проекта — внутри этой папки.** Материалы курса (папки воркшопов) не трогай и в репозиторий проекта не добавляй.

## Правила работы агента
6. **Запускай и проверяй код сам.** Локально, через расширение IDE — не проси владельца выполнять команды в терминале вручную. Перед запуском нового процесса убей старый (бот, dev-сервер, API).
   *Почему:* старый процесс держит порт и работает на прежнем коде. Правки не подхватятся, а бот при двух живых копиях перестаёт отвечать — Telegram отдаёт обновления только одному получателю. Отладка уходит в поиск несуществующей ошибки в коде.
7. **Уточняющие вопросы задавай компактно.** Одним коротким списком с вариантами, а не по одному длинными сообщениями. Всё, что можешь решить сам разумным умолчанием, — решай и говори, что выбрал.
   *Почему:* воркшоп идёт по таймеру. Пять вопросов подряд в отдельных сообщениях съедают время, которого потом не хватит на отладку.
8. **Пиши на стеке проекта.** Next.js + TypeScript + Prisma + PostgreSQL — библиотеки под задачу выбирай сам, лишних вопросов не задавай. Websocket не используй: где он есть или напрашивается — делай обычный HTTP с поллингом.
   *Почему:* на части VPS websocket не проходит через прокси и падает уже на сервере, а не локально. Поллинг работает везде и в этом проекте по нагрузке ничем не хуже.
