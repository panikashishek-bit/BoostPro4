# Журнал обращений: что фиксируем по каждому клиенту

> Основание — `../docs/context.md`, `./role.md`, методология Next Move Theory / AJTBD.
> Дата: 2026-08-30.

---

## 1. Что это и зачем

Таблица, где **одна строка = одно обращение** клиента к боту, и главное в ней — **до какого шага цепочки клиент дошёл и где сорвался**.

### Почему не «записи на услугу»

Состоявшиеся записи уже лежат в БД продукта (`POST /api/bookings`). Вторая копия не даёт нового знания и со временем разойдётся с оригиналом.

Ценность ровно в обратном: **несостоявшиеся обращения сейчас исчезают бесследно.** Клиент написал вечером, не нашёл удобного времени, ушёл — в системе не осталось ничего. Большая задача администратора (Big Job) — «загрузить исполнителей работой и не терять клиентов» — этими данными не обслуживается ничем.

### Почему именно точка обрыва

Задача клиента (Core Job) закрывается только когда пройдут все три шага подряд (Critical Chain of Jobs, см. `role.md` §2):

| Шаг | Задача клиента |
|---|---|
| J1 | понять, что подходит и сколько стоит |
| J2 | увидеть, когда реально свободно |
| J3 | закрепить время за собой |

Ключевой момент (Aha moment) — на J3. Обрыв на J1 и обрыв на J2 требуют **разных** действий владельца: первый лечится базой знаний, второй — графиком и набором мастеров. Без отметки, где именно сорвалось, оба выглядят одинаково — «клиент не записался».

## 2. Единица записи — обращение, не сообщение

Строка пишется на **сессию**. Сессия закрывается по любому из трёх событий:

| Событие | Итог сессии |
|---|---|
| `create_booking` вернул успех | закрывается сразу, `outcome = записался` |
| 30 минут молчания | закрывается по таймауту, итог — по последнему достигнутому шагу |
| `/start` | закрывает предыдущую сессию, начинает новую |

Отдельного хранилища для этого не нужно: в `memory.ts` уже есть `updatedAt` на чат — таймаут считается из него.

## 3. Колонки

### Ядро — обязательные

| Колонка | Тип | Значения | Как заполняется |
|---|---|---|---|
| `session_id` | text | `<chat_id>-<unix ts начала>` | авто. Ключ строки — чтобы дописывать, а не плодить дубли |
| `started_at` | datetime | | первое сообщение сессии |
| `ended_at` | datetime | | момент закрытия |
| `chat_id` | number | | Telegram chat id. Опознаёт повторные обращения одного человека |
| `phone` | text | | телефон клиента, если он его назвал. Нормализуется через `phone.ts`. Пусто, если не назвал — бот его не выпрашивает |
| `channel` | enum | `текст` · `голос` | из типа апдейта grammY (`message:text` / `message:voice`) |
| `intent` | enum | `вопрос` · `запись` · `отмена/перенос` · `прочее` | метка LLM на закрытии сессии |
| `service` | text | | из аргументов `find_free_slots` / `create_booking`; иначе метка LLM |
| `master` | text | | если клиент спрашивал конкретного мастера; иначе пусто |
| **`reached`** | enum | `J1` · `J2` · `J3` | **детерминированно, по вызовам инструментов** (см. §4) |
| **`outcome`** | enum | `записался` · `ушёл` · `бот не смог` | `записался` = был успешный `create_booking`; `бот не смог` = ошибка API или ответ «не знаю»; иначе `ушёл` |
| **`break_reason`** | enum | см. список ниже | только когда `outcome ≠ записался` |
| `booking_id` | text | | если записался — связь со строкой в БД продукта |
| `unanswered_question` | text | | дословный вопрос, на который бот ответил «не знаю». Пусто, если такого не было |

**Значения `break_reason`:** `нет удобного времени` · `нет нужного мастера` · `бот не знал ответа` · `спросил про отмену/перенос` · `спросил про оплату` · `ошибка API` · `ушёл молча` · `другое`.

### Полезные — если несложно

| Колонка | Тип | Зачем |
|---|---|---|
| `messages` | number | сколько сообщений написал клиент. Косвенно — сколько сил ушло |
| `duration_sec` | number | `ended_at − started_at`. Прямая проверка критерия успеха «запись занимает минуту» |
| `name` | text | имя, если клиент назвал. Нужно только чтобы читать журнал глазами |

### Чего в таблице сознательно НЕТ

| Не пишем | Почему |
|---|---|
| Полный текст переписки | Он уже в `data/history.json` с TTL 7 дней. Дублировать — значит удлинять срок хранения контактов задним числом |
| Оценки, теги настроения, «качество ответа» | Не превращаются в действие владельца. Каждая такая колонка — работа на заполнение без решения на выходе |

## 4. Как определяется `reached` — и где детект честно не работает

**J2 и J3 берутся из кода надёжно**, без участия модели:

| Значение | Условие |
|---|---|
| `J3` | в сессии был вызов `create_booking`, вернувший успех |
| `J2` | был вызов `find_free_slots` |
| `J1` | инструменты не вызывались вовсе |

**J1 инструментом не детектится.** База знаний вклеена в системный промпт (`knowledge.ts` → `prompt.ts`), вызова нет — значит по логу инструментов не видно ни что клиент спросил, ни что бот не смог ответить.

**Решение — не LLM-классификатор, а фиксированная формула отказа.** В `character.md` ответ на неизвестное уже имеет устойчивую форму: «не подскажу, не хочу вводить в заблуждение». Достаточно закрепить её в промпте как обязательную дословную фразу-маркер — и `unanswered_question` вместе с `break_reason = бот не знал ответа` ловятся точным поиском подстроки: бесплатно, без второго вызова модели и без вероятностной ошибки.

Метка LLM остаётся нужна только для `intent` и для `break_reason` в неоднозначных случаях — один дешёвый вызов на закрытии сессии, не на каждое сообщение.

## 5. Где лежит

`./data/sessions.csv` — дописывание строк, рядом с `history.json`.

- Файл **в `.gitignore`** (там имена и телефоны клиентов), как и `history.json` и `.env`. В `project/.gitignore` это покрыто правилом `bot_administrator/data/`.
- **Телефон — персональные данные.** Раз он в журнале, у журнала должен быть срок хранения, как у `history.json` (там TTL 7 дней). Иначе таблица тихо станет бессрочной базой контактов — а она нужна для разбора обрывов, а не для накопления номеров. При переезде в Google Sheets проверить, что доступ к листу не «по ссылке всем».
- Колонки заданы так, что при переезде в Google Sheets менять не придётся ничего — те же заголовки.
- Строка пишется **на закрытии сессии**, одним движением. Провал записи в журнал не должен ронять диалог — тот же принцип, что в `memory.ts`: «разговор важнее журнала».

## 6. Что владелец с этим делает

| Что видно в таблице | Действие |
|---|---|
| Много `J2` + `нет удобного времени` | расширить график или добавить смену — спрос есть, ёмкости нет |
| Много `J2` + `нет нужного мастера` | перегруз конкретного мастера; спрос концентрированный |
| Повторяющиеся `unanswered_question` | пополнить `../faq/` — очередь по частоте, а не по догадкам |
| Много `спросил про отмену/перенос` | сигнал, что граница продукта задевает клиентов чаще, чем ожидалось |
| `duration_sec` ползёт вверх | критерий успеха «запись за минуту» проседает — смотреть, на каком шаге |

Три верхние строки — это варианты 2 и 3 из обсуждения: они получаются фильтром по этой же таблице, отдельные заводить не нужно.
