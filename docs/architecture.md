# Архитектура

Учебный проект «ПроСервис» — онлайн-запись на услуги. Next.js-приложение (монолит), база PostgreSQL, доступ к данным только через Prisma.

Рядом с приложением живёт **второй процесс** — Telegram-бот-администратор в `bot_administrator/`. Он запускается отдельно, имеет свои зависимости и свой `.env`, и с приложением общается только по HTTP.

## Из чего состоит

```
Браузер                        Telegram
   │                              │
   │                              │  long polling (HTTP)
   │                              ▼
   │                       bot_administrator/
   │                       отдельный процесс (Node + grammY)
   │                              ┆
   │                              ┆  HTTP + x-api-key
   ▼                              ┆
Next.js App Router                ┆
  ├─ / (главная)                  ┆   server components
  ├─ /book (запись)               ┆   + server actions
  ├─ /admin (админка)             ┆
  └─ /api/* (REST)  ◄┄┄┄┄┄┄┄┄┄┄┄┄┄┘
          │
   Prisma Client (singleton)
          │
   PostgreSQL (docker-compose)
```

Части:

- **Публичная витрина** (`src/app/page.tsx`) — список активных услуг, ссылка-диплинк на запись с предвыбором услуги (`/book?service=<id>`).
- **Мастер записи** (`src/app/book/`) — серверная страница отдаёт список услуг, клиентский компонент `BookWizard` ведёт по шагам: услуга → мастер → дата → слот → контакты.
- **Админка** (`src/app/admin/`) — три вкладки: записи, услуги, команда. Вход по паролю.
- **REST API** (`src/app/api/`) — `services`, `masters`, `availability`, `bookings`.
- **Общая логика** (`src/lib/`) — `prisma.ts` (клиент), `availability.ts` (расчёт слотов), `format.ts` (цены, длительность, дата-время в ru-RU).
- **Бот-администратор** (`bot_administrator/`) — отдельный Node-процесс на TypeScript и grammY. Отвечает клиентам в Telegram. Сейчас каркас: принимает текст и отвечает заглушкой; API приложения ещё не вызывает. Рядом с кодом лежат его роль (`role.md`), характер (`character.md`) и `.env` с токеном. База знаний, на которой он отвечает клиентам, — в `faq/` в корне проекта.

## Как части общаются

Три разных пути к данным — по назначению:

| Кто | Как читает | Как пишет |
|---|---|---|
| Публичные страницы, вкладки админки | Prisma напрямую в server component | — |
| `BookWizard` (клиентский) | `fetch` в REST `/api/*` | `POST /api/bookings` |
| Формы админки | — | server actions (`admin/actions.ts`) + `revalidatePath` |
| Бот-администратор (внешний процесс) | `fetch` в REST `/api/*` с ключом `x-api-key` | `POST /api/bookings` с тем же ключом |

Причина разделения: страницы рендерятся на сервере и им не нужен HTTP-хоп до самих себя; визард интерактивен и подгружает мастеров и слоты по мере выбора, поэтому ему нужен именно API; формы админки — обычные `<form>`, для них server actions короче, чем свои эндпоинты.

Все маршруты помечены `export const dynamic = "force-dynamic"` — данные всегда свежие, кэша страниц нет.

### Шлагбаум перед `/api/*`

У этих ручек два потребителя с разными правами, и это определяет всю конструкцию:

| Кто | Откуда | Ключ |
|---|---|---|
| Форма записи на сайте | Браузер, тот же origin | Не может быть: любой ключ в клиентском коде видно в исходниках страницы |
| Бот-администратор | Внешний процесс | `x-api-key`, значение — `APP_API_KEY` |

`src/middleware.ts` пропускает запросы, у которых браузер проставил `Sec-Fetch-Site: same-origin` (или `same-site`), а всем остальным требует ключ. Файлы самих ручек при этом не меняются — они ничего не знают про авторизацию.

**Почему не потребовать ключ со всех.** Форма записи ходит в `/api/*` из браузера. Дать ей ключ — значит опубликовать его: он попадёт в бандл страницы. Тогда защита исчезает, а ключ ещё и утекает.

**Ключ не задан — снаружи не пускаем никого** (`503`). Сайт при этом продолжает работать. Молча открыть доступ было бы опаснее: поломка заметна сразу, а тихо снятая защита — нет.

**⚠️ Это учебный шлагбаум, как и пароль админки.** Заголовок `Sec-Fetch-Site` подделывается вручную одной строкой в curl, так что от целенаправленной атаки он не защищает — он закрывает ручки от случайного и автоматического доступа снаружи.

## Модель данных

```
Service ──< MasterService >── Master ──< WorkingHour
   │                            │
   └────────< Booking >─────────┘
```

- **Service** — услуга: цена (`priceRub`), длительность (`durationMin`), флаг `isActive`.
- **Master** — исполнитель: имя, специализация, `isActive`.
- **MasterService** — кто какие услуги делает (many-to-many, составной ключ).
- **WorkingHour** — недельный график мастера: день недели (1 = понедельник … 7 = воскресенье) и окно в минутах от полуночи (`600` = 10:00).
- **Booking** — запись: мастер, услуга, `startAt`/`endAt`, статус (`CONFIRMED` / `CANCELLED` / `DONE`), имя и телефон клиента, комментарий.

Длительность и время хранятся в минутах от полуночи и в абсолютных `DateTime` — без строк вроде `"10:00"`, чтобы арифметика пересечений была тривиальной.

## Бот-администратор

Живёт в `bot_administrator/` **отдельным npm-пакетом**: свой `package.json`, свои `node_modules`, свой `.env`. Приложение о нём ничего не знает.

```
bot_administrator/
  src/bot.ts        точка входа: обработчики и запуск
  src/config.ts     чтение и проверка переменных окружения
  src/prompt.ts     сборка системной инструкции из role.md + character.md + faq/
  src/knowledge.ts  чтение базы знаний из ../faq/
  src/llm.ts        один ход разговора с моделью через OpenRouter
  src/agent.ts      цикл: модель → инструмент → модель → ответ клиенту
  src/tools.ts      инструменты: показать свободное время, оформить запись
  src/api.ts        HTTP-клиент API приложения
  src/speech.ts     расшифровка голосовых через AssemblyAI
  src/phone.ts      приведение телефона к единому виду
  src/retry.ts      повторы при временных сбоях и понятные клиенту ошибки
  src/memory.ts     история диалога по чатам, с сохранением на диск
  data/history.json переписка клиентов — в git не попадает
  role.md           роль (поддержка) и джобы под реализацию
  character.md      характер и тон общения — идёт в системную инструкцию
  .env              секреты, в git не попадает
  .env.example      имена переменных без значений
```

| Что | Как |
|---|---|
| Стек | TypeScript, запуск через `tsx` (уже есть в приложении) |
| Библиотека | grammY — TS-first клиент Telegram Bot API |
| Связь с Telegram | Long polling: бот сам опрашивает Telegram по HTTP |
| Модель | `google/gemini-2.5-flash` через OpenRouter (API совместим с OpenAI — хватает `fetch`) |
| Распознавание речи | AssemblyAI, официальный SDK `assemblyai`, модель `universal-2` |
| Секреты | `bot_administrator/.env`, читается штатным `node --env-file` |
| Доступ к API приложения | `APP_API_URL` (адрес) и `APP_API_KEY` (ключ) в `bot_administrator/.env`. Адрес переменной, а не константой: при переезде на сервер меняется одна строка |
| Запуск | `npm start` в `bot_administrator/` (`npm run dev` — с перезапуском на правках) |

### Как бот отвечает

```
сообщение из Telegram
        │
        ▼
  история чата (последние 5 пар) ──┐
                                   ├──► OpenRouter (gemini-2.5-flash) ──► ответ клиенту
  системная инструкция ────────────┘
  = роль + характер + вся база знаний из faq/
```

**Системная инструкция собирается при старте, а не на каждое сообщение.** Из `role.md` и `character.md` берутся не файлы целиком, а конкретные разделы: остальное — внутренние заметки (обоснования, планы), модели они не нужны и уводят её в разговор о продукте вместо услуг. База знаний — все файлы `faq/*.md`, кроме `README.md`: он инструкция для нас, а не факты для клиента.

**Вся база знаний уходит в каждый запрос целиком.** Она небольшая (~10 КБ), поэтому поиск по ней (RAG) не нужен — модель видит всё сразу и не может «не найти» нужный файл. Если база вырастет в разы, этот выбор придётся пересмотреть.

**Правило «не знаю» задано явно в инструкции.** Модель по умолчанию охотно достраивает правдоподобное: придумает цену, услугу или адрес. Выдуманный ответ клиент проверит на месте, и это дороже честного «не подскажу, уточните по телефону».

**Память диалога переживает перезапуск.** `Map` по `chat_id`, последние 10 сообщений (5 пар «вопрос — ответ»), с записью в `data/history.json` при каждом изменении.

Сначала память жила только в процессе — и это оказалось не мелочью. При перезапуске бота клиент оставался посреди записи с собеседником, который забыл, о какой услуге шла речь, и переспрашивал заново. На сервере так вело бы себя каждое обновление кода.

Файл пишется через временный с последующим переименованием — обрыв на середине не оставит битый JSON. Не прочитался — бот стартует с пустой историей и продолжает работать: потерять переписку неприятно, не работать вовсе — хуже.

**⚠️ В `data/history.json` лежат имена и телефоны клиентов.** Каталог в `.gitignore`. Переписка старше 7 дней удаляется при старте: хранить контакты дольше, чем нужно для записи, незачем.

**Сбой модели не оставляет клиента без ответа.** Если OpenRouter недоступен или отвечает ошибкой, бот извиняется и даёт телефон салона, а неудачный обмен в историю не пишет — иначе он мешал бы следующим ответам.

### Инструменты: как бот делает дела

Модель сама решает, чего хватит — ответа по базе знаний или вызова API:

| Инструмент | Что делает | Куда ходит |
|---|---|---|
| `find_free_slots` | Показывает свободное время на дату | `services` → `masters` → `availability` |
| `create_booking` | Оформляет запись | то же + `POST /api/bookings` |

**Модель работает названиями, а не идентификаторами.** Инструменты принимают «Маникюр» и «Анна»; разрешение названий в cuid спрятано в `tools.ts`. API при этом не менялось. Иначе модели пришлось бы тащить два cuid через три хода — именно на этом она чаще всего и ошибается.

**Время записи берётся из ответа приложения, а не из аргументов модели.** `create_booking` получает метку вроде `«15:00»`, находит по ней слот в свежем ответе `availability` и отправляет его `startISO`. Так исключаются часовые пояса и выдуманное время.

**Перед тем как назвать время, бот обязан перезапросить `find_free_slots`.** Это не украшение: на проверке модель переиспользовала список из своей же реплики двумя ходами раньше и предложила четыре занятых времени из пяти — запись, сделанная в промежутке, list не обновила. Правило прописано и в системной инструкции, и в описании самого инструмента.

**Сбой инструмента не роняет разговор.** Текст ошибки уходит модели как результат вызова, и она объясняет клиенту, что не получилось. Ответ `409` от приложения — не поломка, а рабочий случай «время только что заняли»: бот предлагает другое.

**Телефон нормализуется в коде и подтверждается у клиента.** Клиенты называют номер как придётся — «911-70-201-20», «8 921 555 33 22», «+7 (911) 702-01-20»; код страны чаще всего опускают. `phone.ts` сводит всё к одному виду `+7 9XX XXX-XX-XX`, а непохожее на мобильный отклоняет.

Первый вызов `create_booking` запись НЕ создаёт: инструмент возвращает номер в правильном виде и требование прочитать его клиенту. Записывает только повторный вызов с `phoneConfirmed: true`. Гейт стоит в коде, потому что по этому номеру администратор звонит, если что-то меняется, а ошибиться в цифрах на слух легко.

**Календарь ближайших дней уходит в каждый запрос.** Модель переводила «в четверг» в число через раз: на одной формулировке справлялась, на другой переспрашивала у клиента число. Готовая таблица из восьми дней снимает вопрос — выбрать строку надёжнее, чем вычислить.

**Ограничение в четыре обращения к API за один ответ.** Больше пары не нужно (посмотреть время → записать), а цикл без предохранителя сжёг бы лимит и деньги.

**История диалога хранит только текст**, без служебных сообщений об инструментах: цикл вызовов каждый раз начинается заново, память остаётся маленькой и читаемой.

### Голосовые сообщения

```
голосовое в Telegram → бот скачивает файл → AssemblyAI (universal-2)
   → текст → та же дорога, что у обычного сообщения
```

Режим pre-recorded: метод `transcribe()` из SDK сам загружает аудио и дожидается результата, поэтому upload и опрос статуса вручную писать не нужно. Ключ уходит в заголовок `Authorization` как есть, без префикса `Bearer`.

**Файл скачиваем сами, а не даём AssemblyAI ссылку от Telegram.** У ссылки вида `api.telegram.org/file/bot<ТОКЕН>/…` токен прямо в адресе — отдать её стороннему сервису значит отдать бота.

**Модель задаётся через `speech_models: ["universal-2"]`, а не `speech_model`.** В типах SDK поле `speech_model` знает только `best`, `nano`, `slam-1` и `universal`, а `speech_models` принимает названия строками.

**Язык определяется автоматически** (`language_detection: true`): клиенты пишут по-русски, иногда по-английски.

**Бот показывает, что расслышал**, отдельной строкой перед ответом. Распознавание ошибается, и клиент должен заметить это сразу, а не после того, как его запишут не на ту услугу.

**Язык ответа выбирается кодом, а не правилом.** Инструкция «отвечай на языке клиента» не срабатывала: вся инструкция и вся база знаний на русском, и модель отвечала по-русски даже на английский вопрос. Теперь язык сообщения определяется подсчётом кириллицы против латиницы, и в каждый запрос добавляется явное указание. Правило модель может проигнорировать, отдельное сообщение — нет.

**Голосовое не разобралось — бот просит написать текстом**, а не молчит и не выдумывает.

**Почему отдельный пакет, а не часть Next.js.** Бот — долгоживущий процесс с опросом Telegram, приложение — веб-сервер, отвечающий на запросы. У них разный жизненный цикл: бота можно перезапустить, не трогая сайт, и наоборот. Разные зависимости и разные секреты тоже проще держать врозь.

**Почему long polling, а не webhook.** Вебхуку нужен публичный HTTPS-адрес — локально его нет, пришлось бы поднимать туннель. Long polling работает и с ноутбука, и с сервера без входящих портов. Это обычный HTTP-запрос, а не websocket: на части VPS websocket не проходит через прокси.

**Важно: одновременно должен работать только один экземпляр бота.** Telegram отдаёт обновления единственному получателю — при двух живых процессах бот начинает «терять» сообщения и отвечать через раз. Перед запуском старый процесс нужно убивать.

**Переменные окружения читает `config.ts`, а не код напрямую.** Отсутствующая переменная роняет бот сразу и с внятным текстом, а не позже и непонятно.

## Поведение при сбоях

Внешних сервисов три — приложение, OpenRouter, AssemblyAI — и каждый иногда не отвечает. Правило одно: **клиент не видит технической ошибки, он видит следующий шаг.**

| Что сломалось | Что делает бот | Что видит клиент |
|---|---|---|
| Сеть моргнула, `429`, `5xx` | Повторяет: 0.5 с, затем 1.5 с | Ничего — обычно успевает восстановиться |
| Приложение или база лежат | Повторил, не помогло | «Расписание сейчас недоступно» + телефон салона |
| Лимит запросов к модели | Повторил, не помогло | «Сейчас очень много обращений» + телефон |
| Ключ протух, `401` | Не повторяет — бессмысленно | «Я временно не могу ответить» + телефон |
| Голосовое не разобралось | — | «Не получилось разобрать, напишите текстом» |
| Всё прочее, неожиданное | Ловит `bot.catch` | «Что-то пошло не так» + телефон |

**Повторяем только временные сбои.** `408`, `429` и `5xx` — шум, который проходит сам. `400`, `401`, `404`, `409` — второй раз ответят так же, повтор только тратит время клиента.

**Технический текст не доходит до модели.** Раньше в неё уходило `API /api/services ответил 500`, и она могла это пересказать клиенту. Теперь `ServiceError` несёт два текста: подробный — в лог, человеческий — модели. Клиенту нужно знать, что делать, а не что сломалось.

**Ручки `/api/*` при падении отдают JSON `503`, а не пустой `500`.** Обёртка `withErrorHandling` ловит всё необработанное. Код `503`, а не `500`, потому что база может подняться и повторить запрос имеет смысл.

**Консультация переживает падение базы.** Цены, услуги и часы работы бот берёт из `faq/`, а не из API, — поэтому при лежащей базе он продолжает отвечать на вопросы и не может только показать свободное время.

**Границы ввода.** Сообщение длиннее 2000 символов бот не отправляет модели, голосовое длиннее трёх минут не расшифровывает, свой ответ обрезает до 3900 символов по границе предложения — Telegram не принимает длиннее 4096, и такой ответ не дошёл бы вовсе.

## Как это живёт на сервере

Бокс — Ubuntu 24.04, 2 ГБ памяти, 2 ядра. **Node на нём нет, есть Docker** — поэтому всё едет контейнерами, ничего доустанавливать не пришлось.

```
GitHub: push в main
      │
      ▼
GitHub Actions ──scp──► /home/uno/app         статика штаба (Воркшоп 1)
      │
      └─────scp──────► /home/uno/proservice   исходники
                              │
                              ├─ .env         пишется из секретов, только на сервере
                              └─ docker compose up -d --build
                                     │
                     ┌───────────────┼───────────────┐
                     ▼               ▼               ▼
                    db              app             bot
                postgres:17    Next.js :3000    grammY + tsx
                                     ▲               │
                                     └───────────────┘
                                    APP_API_URL=http://app:3000
```

**`APP_API_URL` — это `http://app:3000`, имя сервиса в сети compose.** Не `localhost`: для бота в своём контейнере `localhost` — это он сам. И не публичный адрес: API незачем выставлять наружу, а внутренняя сеть не зависит от файрвола.

**Порт приложения открыт только на `127.0.0.1`.** Порт 80 на сервере занят статикой штаба, её не трогаем; API снаружи не нужно — в него ходит только бот, изнутри.

**`restart: unless-stopped` у всех трёх контейнеров.** Это и есть «работает без моего компьютера»: сервисы поднимаются сами после падения и после перезагрузки сервера.

**Секретов в репозитории нет.** `.env` собирается на сервере во время деплоя из GitHub Secrets, с правами `600`. В git не попадает ни он, ни его значения.

**История диалогов и база — на именованных томах.** Без них передеплой стирал бы записи клиентов и обрывал разговоры на середине.

**Seed наливается только в пустую базу.** Он начинается с `deleteMany` — на живой базе стёр бы реальные записи. Workflow сначала считает услуги и наливает, только если их ноль.

**Схема накатывается при каждом старте приложения** (`prisma db push` идемпотентен) — отдельного шага миграции нет, потому что в проекте нет и миграций.

**Прокси не понадобился.** Бокс стоит в Амстердаме, и Telegram, OpenRouter и AssemblyAI с него отвечают напрямую — проверено до выкатки.

**`bot_administrator` исключён из `tsconfig.json` приложения.** Иначе сборка Next тянет файлы бота на проверку типов и падает на импорте `grammy`: у бота отдельный пакет со своими зависимостями, в образ приложения они не попадают.

## Ключевые технические решения

**Слоты считаются на лету, не хранятся.** `getAvailableSlots` берёт окна графика мастера на нужный день недели, нарезает их шагом 30 минут под длительность конкретной услуги и выбрасывает те, что пересекаются с активными бронями или уже прошли. Плюс: нет таблицы слотов, которую надо генерировать и чистить; изменил график — расписание пересчиталось само. Минус: каждый запрос доступности — два запроса к базе.

**Двойная проверка занятости.** Свободные слоты — это подсказка, а не бронь. Финальная проверка пересечения делается ещё раз внутри `POST /api/bookings`, и при конфликте возвращается `409`. Без неё два клиента, открывшие форму одновременно, записались бы на одно время.

**Prisma-клиент как singleton на `globalThis`.** В dev-режиме Next.js перезагружает модули при каждом изменении файла; без singleton каждый hot-reload открывал бы новый пул подключений к PostgreSQL.

**Авторизация админки — один пароль в httpOnly-cookie.** `login` сверяет введённое с `ADMIN_PASSWORD` и кладёт значение в cookie на 8 часов; каждое действие в `actions.ts` начинается с `ensureAuth()`. Это учебный шлагбаум, а не система авторизации: нет ролей, нет пользователей, нет хеширования — cookie хранит сам пароль.

**Наборы связей заменяются транзакцией.** `setServiceMasters` / `setMasterServices` делают `deleteMany` + `createMany` в одной транзакции, а не вычисляют дельту. Проще и безопаснее при небольших наборах.

**Домен задаётся seed-данными, а не кодом.** Модель обобщённая — «услуга + исполнитель + слот + запись». В `prisma/seed.ts` для наглядности налит салон; чтобы получить автосервис или репетитора, достаточно поменять seed, схему трогать не нужно.

## Ограничения текущей реализации

- Время считается в **локальной таймзоне сервера** — при разнесённых сервере и клиенте слоты уедут.
- Приложение на сервере доступно **только изнутри** (`127.0.0.1:3000`): публичной витрины и админки снаружи нет.
- График мастера **только недельный**: нет отпусков, выходных-исключений и перерывов.
- Горизонт записи зашит в клиенте — **60 дней вперёд**, шаг сетки — **30 минут**.
- **Нет миграций**: схема накатывается через `prisma db push`, история изменений базы не ведётся.
- Отмена записи доступна **только в админке**; у клиента нет ни кабинета, ни ссылки на управление своей записью.
- Бот **не умеет отменять и переносить** записи — только смотреть время и записывать. Отмена по-прежнему только в админке.
- Бот **не знает, что клиент записывал раньше**: связки Telegram-аккаунта с телефоном нет.
- Бот понимает текст и голосовые; фото, видео и документы — нет.
- Память диалога ограничена **последними 5 парами сообщений** и хранится 7 дней; более ранний контекст бот не видит.
