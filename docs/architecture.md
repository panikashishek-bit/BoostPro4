# Архитектура

Учебный проект «ПроСервис» — онлайн-запись на услуги. Одно Next.js-приложение (монолит), база PostgreSQL, доступ к данным только через Prisma.

## Из чего состоит

```
Браузер
  │
  ├─ / (главная)      ─┐
  ├─ /book (запись)    │  Next.js App Router
  ├─ /admin (админка) ─┘   server components + server actions
  │                          │
  └─ /api/* (REST) ──────────┤
                             │
                          Prisma Client (singleton)
                             │
                        PostgreSQL (docker-compose)
```

Части:

- **Публичная витрина** (`src/app/page.tsx`) — список активных услуг, ссылка-диплинк на запись с предвыбором услуги (`/book?service=<id>`).
- **Мастер записи** (`src/app/book/`) — серверная страница отдаёт список услуг, клиентский компонент `BookWizard` ведёт по шагам: услуга → мастер → дата → слот → контакты.
- **Админка** (`src/app/admin/`) — три вкладки: записи, услуги, команда. Вход по паролю.
- **REST API** (`src/app/api/`) — `services`, `masters`, `availability`, `bookings`.
- **Общая логика** (`src/lib/`) — `prisma.ts` (клиент), `availability.ts` (расчёт слотов), `format.ts` (цены, длительность, дата-время в ru-RU).

## Как части общаются

Три разных пути к данным — по назначению:

| Кто | Как читает | Как пишет |
|---|---|---|
| Публичные страницы, вкладки админки | Prisma напрямую в server component | — |
| `BookWizard` (клиентский) | `fetch` в REST `/api/*` | `POST /api/bookings` |
| Формы админки | — | server actions (`admin/actions.ts`) + `revalidatePath` |

Причина разделения: страницы рендерятся на сервере и им не нужен HTTP-хоп до самих себя; визард интерактивен и подгружает мастеров и слоты по мере выбора, поэтому ему нужен именно API; формы админки — обычные `<form>`, для них server actions короче, чем свои эндпоинты.

Все маршруты помечены `export const dynamic = "force-dynamic"` — данные всегда свежие, кэша страниц нет.

## Модель данных

```
Service ──< MasterService >── Master ──< WorkingHour
   │                            │
   └────────< Booking >─────────┘
```

- **Service** — услуга: цена (`priceRub`), длительность (`durationMin`), флаг `isActive`.
- **Master** — исполнитель: имя, специализация, `isActive`.
- **MasterService** — кто какие услуги делает (many-to-many, составной ключ).
- **WorkingHour** — недельный график мастера: день недели (1 = понедельник … 7 = воскресенье) и окно в минутах от полуночи (`600` = 10:00).
- **Booking** — запись: мастер, услуга, `startAt`/`endAt`, статус (`CONFIRMED` / `CANCELLED` / `DONE`), имя и телефон клиента, комментарий.

Длительность и время хранятся в минутах от полуночи и в абсолютных `DateTime` — без строк вроде `"10:00"`, чтобы арифметика пересечений была тривиальной.

## Ключевые технические решения

**Слоты считаются на лету, не хранятся.** `getAvailableSlots` берёт окна графика мастера на нужный день недели, нарезает их шагом 30 минут под длительность конкретной услуги и выбрасывает те, что пересекаются с активными бронями или уже прошли. Плюс: нет таблицы слотов, которую надо генерировать и чистить; изменил график — расписание пересчиталось само. Минус: каждый запрос доступности — два запроса к базе.

**Двойная проверка занятости.** Свободные слоты — это подсказка, а не бронь. Финальная проверка пересечения делается ещё раз внутри `POST /api/bookings`, и при конфликте возвращается `409`. Без неё два клиента, открывшие форму одновременно, записались бы на одно время.

**Prisma-клиент как singleton на `globalThis`.** В dev-режиме Next.js перезагружает модули при каждом изменении файла; без singleton каждый hot-reload открывал бы новый пул подключений к PostgreSQL.

**Авторизация админки — один пароль в httpOnly-cookie.** `login` сверяет введённое с `ADMIN_PASSWORD` и кладёт значение в cookie на 8 часов; каждое действие в `actions.ts` начинается с `ensureAuth()`. Это учебный шлагбаум, а не система авторизации: нет ролей, нет пользователей, нет хеширования — cookie хранит сам пароль.

**Наборы связей заменяются транзакцией.** `setServiceMasters` / `setMasterServices` делают `deleteMany` + `createMany` в одной транзакции, а не вычисляют дельту. Проще и безопаснее при небольших наборах.

**Домен задаётся seed-данными, а не кодом.** Модель обобщённая — «услуга + исполнитель + слот + запись». В `prisma/seed.ts` для наглядности налит салон; чтобы получить автосервис или репетитора, достаточно поменять seed, схему трогать не нужно.

## Ограничения текущей реализации

- Время считается в **локальной таймзоне сервера** — при разнесённых сервере и клиенте слоты уедут.
- График мастера **только недельный**: нет отпусков, выходных-исключений и перерывов.
- Горизонт записи зашит в клиенте — **60 дней вперёд**, шаг сетки — **30 минут**.
- **Нет миграций**: схема накатывается через `prisma db push`, история изменений базы не ведётся.
- Отмена записи доступна **только в админке**; у клиента нет ни кабинета, ни ссылки на управление своей записью.
